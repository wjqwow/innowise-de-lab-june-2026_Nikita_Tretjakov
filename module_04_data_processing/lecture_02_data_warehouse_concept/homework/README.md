На основе очищенных данных Silver-слоя спроектирован и реализован Gold Layer для предметной области «Сеть продуктовых магазинов EcoMarket». Gold Layer представляет собой звёздную схему для аналитики продаж. Поверх неё созданы пять денормализованных витрин в схеме `mart`, пригодных для подключения BI-инструмента.

Моделируемый в DWH бизнес-процесс — **розничные продажи в сети продуктовых магазинов EcoMarket**.

Продажи выбраны потому, что это основной процесс компании и предоставленный набор данных содержит полный набор связанных сущностей для его анализа: продажи, товары, категории, клиенты, сотрудники, магазины, города и страны. На основе модели можно отвечать на бизнес-вопросы о выручке, скидках, покупательском поведении, сезонности товаров, результативности сотрудников и географии продаж.

Событие, лежащее в основе анализа, — **покупка одного товара в рамках транзакции, то есть позиция чека**. Источник этого события — `silver.silver_sales`.

В анализе процесса участвуют следующие измерения:

- товар — что продано;
- категория — к какой товарной категории относится товар;
- клиент — кто совершил покупку;
- сотрудник — кто обслужил продажу;
- магазин — где совершена покупка;
- локация — город и страна магазина/продажи;
- дата — в какой день совершена покупка;
- время — в какое время суток совершена покупка.

**Одна строка `gold.fact_sales` = одна товарная позиция с бизнес-ключом `sales_id`: один товар (`product_id`) в одной транзакции (`transaction_number`), купленный одним клиентом (`customer_id`), обслуженный одним сотрудником (`employee_id`) в одном магазине (`shop_id`) в конкретный момент `sales_timestamp`.**

Данные в `fact_sales` не агрегированы: они хранятся на самом детальном транзакционном уровне. Если в одном чеке несколько товаров, каждая позиция является отдельной строкой факта, однако строки объединяются общим `transaction_number`.

Такой grain выбран по следующим причинам:

1. Он даёт максимальную гибкость: данные можно агрегировать по дням, месяцам, магазинам, странам, категориям, клиентам и сотрудникам без потери детализации.
2. Каждая позиция чека учитывается ровно один раз, поэтому суммы выручки и количества товаров не дублируются.
3. В одной таблице фактов не смешиваются метрики разных уровней: здесь нет дневных итогов, итогов по чеку или месячных агрегатов.
4. Все внешние ключи однозначно описывают именно позицию продажи. Например, `product_key` относится к проданному товару, а `shop_key` — к магазину сотрудника, обслужившего эту строку продажи.

Средний чек рассчитывается корректно в два шага: сначала суммы агрегируются до `transaction_number`, затем вычисляется среднее. Это не нарушает grain факта.

Центр звезды — транзакционная таблица `gold.fact_sales`. Вокруг неё расположены восемь измерений: `dim_product`, `dim_category`, `dim_customer`, `dim_employee`, `dim_shop`, `dim_location`, `dim_date`, `dim_time`.

Все связи таблицы фактов используют surrogate keys. Business keys из источника сохраняются в измерениях как отдельные поля и используются при идемпотентной загрузке.

`sales_key` — технический первичный ключ. `sales_id` — business key.

| Метрика            | Правило                                                   |
| ------------------ | --------------------------------------------------------- |
| `quantity`         | `silver.silver_sales.quantity`                            |
| `discount_pct`     | `silver.silver_sales.discount`                            |
| `net_revenue`      | `silver.silver_sales.total_price`; считается суммой после скидки |
| `gross_revenue`    | `round(net_revenue / (1 - discount_pct), 2)`              |
| `discount_amount`  | `gross_revenue - net_revenue`                             |
| `estimated_cost`   | `dim_product.list_price * quantity`                       |
| `estimated_profit` | `net_revenue - estimated_cost`                            |

| -------------- | ------------- | -------------- | ------------- | ------------------------------------------- |
| `dim_product`  | SCD Type 2    | `product_key`  | `product_id`  | товар, цена, класс, срок хранения, признаки |
| `dim_category` | Type 1        | `category_key` | `category_id` | категория товара                            |
| `dim_customer` | Type 1        | `customer_key` | `customer_id` | клиент и его домашняя локация               |
| `dim_employee` | Type 1        | `employee_key` | `employee_id` | сотрудник и назначенный магазин             |
| `dim_shop`     | Type 1        | `shop_key`     | `shop_id`     | магазин, адрес, локация                     |
| `dim_location` | Type 1        | `location_key` | `city_id`     | город, индекс, страна, код страны           |
| `dim_date`     | статическое   | `date_key`     | `full_date`   | календарные атрибуты дня                    |
| `dim_time`     | статическое   | `time_key`     | `full_time`   | время с точностью до секунды                |

`dim_product` — SCD Type 2

`dim_product` — измерение со хранением истории. Оно содержит `valid_from_dt`, `valid_to_dt` и `is_current`.

При первоначальной загрузке для товара создаётся одна current-версия. При изменении названия, категории, цены, класса, признаков `resistant` / `is_allergic` или срока хранения текущая запись закрывается (`is_current = false`, заполняется `valid_to_dt`), а новая версия вставляется как current. Частичный уникальный индекс гарантирует, что у одного `product_id` не может быть более одной current-версии.

При загрузке текущая версия товара сопоставляется с записью `silver.silver_products` по `product_id`. Если один из отслеживаемых атрибутов изменился, SQL сначала закрывает current-версию, затем добавляет новую. Исходный Silver-слой предполагается очищенным: одна актуальная запись на `product_id`.

Type 1-измерения и дедупликация

Для `dim_category`, `dim_location`, `dim_shop`, `dim_customer` и `dim_employee` применяется Type 1: хранилище содержит актуальное состояние атрибутов. Логика сделана в два простых шага: сначала `UPDATE` обновляет запись с тем же business key, затем `INSERT ... WHERE NOT EXISTS` добавляет только отсутствующие записи.

`dim_location` намеренно объединяет атрибуты города и страны. Это денормализованное измерение упрощает аналитические запросы и служит единым справочником для slicers по `country_name` и `city_name` в BI. Его ключом является `city_id`, поскольку каждый город в источнике принадлежит ровно одной стране.

Календарь и время

`dim_date` заполняется уникальными датами из `silver.silver_sales` и содержит дату, номер/название дня недели, ISO-неделю, номер/название месяца, квартал и год. `date_key` имеет формат `YYYYMMDD`.

`dim_time` содержит все секунды суток. `time_key` имеет формат `HHMMSS`; дополнительно рассчитывается `part_of_day`: `Night`, `Morning`, `Afternoon` или `Evening`.

Трансформация Silver → Gold

Скрипт `02_gold_load.sql` выполняет следующие действия в одной транзакции:

1. Создаёт запись о начале запуска в `gold.etl_run`.
2. Загружает и обновляет локации, категории, магазины, клиентов и сотрудников.
3. Обрабатывает продукты по правилам SCD Type 2.
4. Формирует недостающие даты и время для продаж.
5. Присоединяет к `silver.silver_sales` surrogate keys измерений и рассчитывает метрики.
6. Вставляет в `fact_sales` только новые строки, которых ещё нет по `sales_id`.
7. Отмечает успешное завершение запуска в `gold.etl_run`.

Загрузка фактов является инкрементальной и идемпотентной: повторный запуск с тем же набором не создаёт дубликатов, поскольку новая строка добавляется только при отсутствии её `sales_id` в Gold. Все аналитические запросы после загрузки обращаются только к `gold.*`; соединения с `silver.*` в них отсутствуют.

Data Marts для BI

| Витрина                     | Grain                       | Назначение                                                           |
| --------------------------- | --------------------------- | -------------------------------------------------------------------- |
| `mart_daily_anomaly`        | магазин + день              | дневная выручка, среднее за предыдущие 30 дней и отклонение `uplift` |
| `mart_shop_daily`           | магазин + день              | география, адрес, дневная и средняя дневная выручка                  |
| `mart_customer_behavior`    | локация + статус + сегмент  | Active/Inactive, сегмент выручки и количество клиентов               |
| `mart_employee_performance` | сотрудник                   | продажи, выручка, оценочная прибыль и ранги внутри магазина          |
| `mart_product_seasonality`  | локация + категория + месяц | объём, выручка и ранг категории в месяце                             |

Статус клиента — `Active`, если последняя покупка не старше 90 дней относительно максимальной даты продаж набора; иначе `Inactive`. Сегменты выручки: `No purchases`, `Low` (до 100), `Medium` (100–499.99) и `High` (500 и более).

Каждая витрина содержит `location_key`.

Файл `04_analytics.sql` содержит пять запросов только к Gold Layer:

1. выручка и количество товаров по месяцам, странам и категориям;
2. топ-10 клиентов по чистой выручке;
3. результативность сотрудников и оценочная маржинальность;
4. топ товаров по количеству продаж;
5. средний чек по магазинам.

При поступлении новой поставки Silver повторно запускаются `02_gold_load.sql` и `03_marts.sql`. Витрины автоматически используют актуальные данные Gold, так как реализованы как обычные `VIEW`.
